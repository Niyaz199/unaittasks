Нужно переработать концепцию и реализацию Календаря ППР в ветке feature/ppr проекта unaittasks.

Важно:
- сначала проанализировать текущую реализацию календаря,
- затем предложить новую структуру и план доработки,
- и только после этого переходить к коду.

Не нужно слепо копировать текущее состояние календаря или поведение ODIN.
Нужно взять за основу наше финальное целевое видение.

==================================================
КОНТЕКСТ
==================================================

Сейчас модуль ППР уже переведен на правильную модель:
- Группа систем
- Система
- Оборудование

Подсистемы больше нет.

Помещения вынесены в shared-слой через object_rooms.

Календарь ППР сейчас уже существует, но его текущий экран перегружен:
- на одной странице смешаны годовой обзор, месячный экран, day-grid, список позиций, формирование месяца и прочие служебные блоки
- это нужно привести к новой понятной структуре

==================================================
ЦЕЛЕВОЕ ВИДЕНИЕ КАЛЕНДАРЯ ППР
==================================================

Нам нужен календарь из 3 логических уровней.

--------------------------------
УРОВЕНЬ 1. ГОДОВОЙ ОБЗОР ПО ГРУППАМ СИСТЕМ
--------------------------------

Это годовой обзор по выбранному объекту.

Что должно быть:
- выбран объект
- строки = группы систем
- колонки = 12 месяцев
- в ячейках отображаются НЕ количество работ, а суммарные запланированные часы за месяц
- то есть верхний уровень показывает нагрузку по группам систем помесячно

Важно:
- нам НЕ нужна недельная разбивка, как в ODIN
- нужен именно обзор по месяцам
- визуально это должна быть матрица:
  группа систем × 12 месяцев

--------------------------------
УРОВЕНЬ 2. ГОДОВОЙ ОБЗОР ПО СИСТЕМАМ ВНУТРИ ГРУППЫ
--------------------------------

Когда пользователь выбирает группу систем, например "Вентиляция", открывается следующий уровень детализации.

Что должно быть:
- строки = системы внутри выбранной группы
  например: фанкойлы, приточно-вытяжные системы, тепловые завесы и т.д.
- колонки = 12 месяцев
- в ячейках = суммарные запланированные часы по системе за месяц

То есть:
- это такой же годовой обзор,
- но уже не по группам систем, а по системам внутри выбранной группы

Важно:
- этот уровень по структуре должен быть визуально согласован с уровнем 1
- по сути это drill-down:
  группы систем -> системы внутри группы

--------------------------------
УРОВЕНЬ 3. МЕСЯЧНЫЙ ОПЕРАЦИОННЫЙ КАЛЕНДАРЬ ПО ВЫБРАННОЙ СИСТЕМЕ
--------------------------------

Это самый важный момент.

В ODIN на третьем уровне открывается снова годовой вид, где видно, на каком оборудовании висит заявка, а при наведении на часы показывается шаблон заявки.

Нас это НЕ устраивает.

У нас на третьем уровне должен открываться НЕ годовой календарь, а месячный operational-календарь.

Что должно быть:
- выбран объект
- выбрана группа систем
- выбрана система
- открыт конкретный месяц
- есть возможность переключаться между месяцами
- по колонкам должны быть дни выбранного месяца
- по строкам должны отображаться единицы оборудования
- желательно вместе с помещением, чтобы было понятно, где находится оборудование

То есть это уже структура примерно такого вида:
- система
- оборудование
- помещение
- дни выбранного месяца

==================================================
ЧТО ПОКАЗЫВАЕТСЯ В ЯЧЕЙКАХ МЕСЯЧНОГО КАЛЕНДАРЯ
==================================================

В ячейках месячного календаря должны отображаться плановые работы / часы по конкретному оборудованию на конкретную дату.

Важно:
- элементы в ячейках должны быть интерактивными
- пользователь должен понимать, какая именно работа запланирована
- при наведении / открытии нужно видеть шаблон работы
  например: "ТО-1"

То есть на этом уровне работа не должна быть просто абстрактным числом.
Это должна быть конкретная плановая единица, связанная с шаблоном и оборудованием.

==================================================
ИНТЕРАКТИВНОСТЬ И ПЕРЕНОС
==================================================

Это принципиально важно.

На месячном уровне плановые часы / работы должны быть интерактивными.

Пример:
- в ячейке есть "3 часа ТО-1"
- пользователь должен иметь возможность перенести эту работу, например, на неделю вперед

То есть месячный календарь должен быть не просто отчетом, а рабочим инструментом перераспределения нагрузки.

Нужно продумать:
- как именно пользователь будет переносить работу
- drag-and-drop или другое удобное действие
- как показывать, что это за шаблон
- как перенос отражается в данных
- как не ломать уже существующие правила переноса

Важно:
- на этом этапе не менять доменную модель без причины
- использовать уже существующие сущности month plan / plan item / ppr_task, если это совместимо с новой структурой
- но при этом предложить такой UI/UX, который поддерживает реальный перенос в календарной сетке месяца
