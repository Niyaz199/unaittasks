========================
ЧТО УЖЕ ИЗМЕНЕНО В ППР
========================

Ранее в ТЗ была ошибка, и часть архитектуры уже была переделана.

Было:
- Группа систем
- Система
- Подсистема
- Оборудование

Это было неверно.

Целевая модель теперь такая:
- Группа систем
- Система
- Оборудование

То есть:
- подсистема удалена из целевой модели
- оборудование должно быть связано напрямую с системой
- все backend/UI/DB-контракты должны жить без subsystem

Также раньше помещения были ошибочно сделаны как часть ППР.

Теперь правильно:
- помещения должны быть общим справочником системы
- помещения должны быть привязаны к объектам
- помещения должны жить вне ППР
- ППР должен использовать помещения как shared-сущность
- этот же справочник позже должен использоваться в модуле обходов

Shared rooms слой теперь мыслится через object_rooms.

То есть нужно учитывать уже новую целевую доменную модель:
- ppr без subsystem
- rooms как shared-слой через object_rooms

========================
ГЛАВНАЯ НОВАЯ ЗАДАЧА — КАЛЕНДАРЬ ППР
========================

Сейчас календарь ППР выглядит как месячный список/таблица по активным назначениям:
- выбирается месяц
- выбирается система
- можно “сформировать месяц”
- ниже показываются записи по работам
- в таблице есть колонки примерно такого типа:
  система / оборудование / шаблон / исходная дата / плановая дата / статус / действия
- у записей есть кнопка “Перенести”
- текущий экран больше похож на список materialized работ месяца, чем на полноценный календарь

Это НЕ тот итоговый вид, который нужен.

========================
КАКОЙ КАЛЕНДАРЬ НУЖЕН ПО ФАКТУ
========================

Нужен не один экран, а логически 3 уровня представления.

--------------------------------
УРОВЕНЬ 1. ГОДОВОЙ ОБЗОР ПО ГРУППАМ СИСТЕМ
--------------------------------

Нужен верхний обзорный календарь ППР.

Как он должен работать:
- по строкам: группы систем
- по колонкам: 12 месяцев года
- в ячейках: суммарная нагрузка / объем ППР / условный объем работ за месяц
- без разбивки по неделям
- это именно обзор по месяцам, а не понедельный календарь
- задача этого экрана — показать картину нагрузки по году

То есть это матрица:
Группа систем × Месяц

Нужен drill-down:
- по клику на группу систем можно провалиться внутрь

--------------------------------
УРОВЕНЬ 2. ГОДОВОЙ ОБЗОР ПО СИСТЕМАМ ВНУТРИ ГРУППЫ
--------------------------------

После выбора группы систем нужно показать детализацию:
- по строкам: системы выбранной группы
- по колонкам: 12 месяцев года
- в ячейках: суммарная нагрузка / объем работ по системе за месяц
- также без разбивки по неделям

То есть это матрица:
Система × Месяц

Так как подсистема удалена из модели, drill-down теперь должен быть:
Группа систем -> Системы

А не:
Группа систем -> Подсистемы

--------------------------------
УРОВЕНЬ 3. ДЕТАЛЬНЫЙ КАЛЕНДАРЬ ВЫБРАННОГО МЕСЯЦА
--------------------------------

Когда пользователь открывает конкретный месяц, например декабрь:
- он должен видеть уже НЕ агрегированную таблицу по месяцам,
- а полный месяц по дням: 1..30/31
- на этом уровне должны быть видны конкретные работы / задания / позиции месяца
- инженер должен видеть, на какие даты реально попали работы

Ключевой рабочий сценарий:
- после генерации месяц может сформироваться так, что много работ сваливаются на 1 число
- инженер должен прямо в этом месячном календаре перераспределить эти работы по другим датам месяца
- перенос должен менять плановую дату конкретной работы / позиции плана / materialized задачи
- перенос не должен ломать шаблон ППР и нормативную периодичность

Иными словами:
- годовой уровень = аналитика и обзор
- месячный уровень = оперативное планирование и ручное распределение нагрузки

========================
КАКОЙ UX/WORKFLOW НУЖЕН
========================

Нужно продумать и описать workflow календаря:

1. Система формирует план на месяц
2. Работы изначально могут иметь базовую/исходную дату, например первое число месяца
3. Инженер открывает месяц
4. Видит все работы этого месяца
5. Переносит часть работ на другие дни внутри месяца
6. После этого исполнители работают уже по новым плановым датам

Важно разделить:
- исходную/расчетную дату
- фактическую плановую дату после ручного переноса

Также нужно продумать:
- как показывать статус записей
- можно ли переносить уже materialized задачи
- что делать с закрытыми/отмененными задачами
- как вести себя при переносе между днями
- допускается ли перенос между месяцами или только внутри месяца
- как делать массовый перенос
- как отображать нагрузку по группам/системам в агрегированных видах
