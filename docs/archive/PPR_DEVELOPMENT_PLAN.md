# План развития модуля ППР

## 1. Текущий приоритет

Главная задача текущего этапа не расширение функционала, а исправление архитектурной базы:

- удалить `subsystem` из целевой модели
- вынести помещения из PPR в общий справочник `object_rooms`
- сохранить PPR отдельным модулем внутри общего проекта

## 2. Порядок разработки

### Этап 1. Shared rooms

- ввести `object_rooms`
- перевести страницу `/ppr/rooms` на shared-layer
- подготовить `lib/object-rooms.ts` и `app/actions/object-room-actions.ts`

### Этап 2. System-based шаблоны

- перевести `ppr_work_templates` на `system_id`
- переписать формы и actions шаблонов
- убрать совместимость по подсистеме

### Этап 3. Equipment и assignments

- перевести оборудование на модель `object -> system -> room`
- перевести назначения на совместимость по системе

### Этап 4. Calendar и tasks

- убрать `subsystem_id` из month plan и task-layer
- переписать scheduler и SQL materialization
- сохранить существующий workflow заявок

### Этап 5. Cleanup

- удалить маршрут и UI подсистем
- удалить legacy-таблицы и legacy-колонки
- синхронизировать документацию

## 3. Что не делаем на этом этапе

- не переносим `ppr_tasks` в обычные `tasks`
- не смешиваем ППР с обходами
- не вводим новый тип заявки вместо отдельного PPR-домена
- не расширяем offline-first и не меняем инфраструктурный каркас

## 4. Риски

- главный риск в цепочке `templates -> assignments -> month plan -> tasks`
- до переключения scheduler и SQL materialization нельзя удалять старые поля
- rooms нельзя оставлять в `ppr_*`, иначе будущий модуль обходов получит лишнюю зависимость от ППР

## 5. Критерий завершения

Этап считается завершенным, когда:

- в коде и БД нет runtime-зависимости от `subsystem`
- помещения живут в `object_rooms`
- PPR UI работает только с `system` и `room`
- документация репозитория описывает новую модель, а не старую
