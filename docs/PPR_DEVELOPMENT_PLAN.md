# План разработки модуля ППР

## 1. Цель плана

Этот документ фиксирует рекомендуемый порядок реальной разработки модуля `ppr` внутри существующего проекта `unaittasks`.

Цели:

- внедрить ППР как отдельный модуль
- не смешать ППР с текущими `tasks`
- максимально переиспользовать текущий каркас проекта
- держать разработку поэтапной и безопасной

---

## 2. Общая стратегия разработки

Разработка должна идти не "с экрана заявки", а от базы предметной модели к пользовательским сценариям:

1. Сначала базовая структура и права.
2. Затем оборудование и QR.
3. Затем шаблоны и назначения.
4. Затем календарь.
5. Затем ППР-заявки.
6. Затем полировка прав, mobile UX и cron.

Такой порядок минимизирует переделки:

- календарь опирается на назначения
- заявки опираются на календарь
- QR опирается на оборудование и активные заявки
- RLS и SQL helper functions должны закладываться с ранних этапов, а не только в финале

UI модуля `ppr` реализуется в текущем UI-подходе проекта:

- без локального внедрения `shadcn/ui`
- на существующих layout, navigation и `components/ui/*`

---

## 3. Итоговый набор артефактов

В результате реализации должны появиться:

- новый модуль `app/(dashboard)/ppr`
- новый API namespace `app/api/ppr`
- новые action-файлы `app/actions/ppr-*.ts`
- новый слой `lib/ppr/*`
- новый UI-слой `components/ppr/*`
- набор миграций `0010+_ppr_*.sql`
- новый набор object-bound таблиц `ppr_*`
- RLS для всех таблиц ППР
- QR-сценарий
- cron-сценарии генерации и переноса
- обязательные unique constraints и индексы для ключевых `ppr_*` таблиц

---

## 4. Порядок миграций

Рекомендуемый порядок SQL-файлов:

1. `0010_ppr_structure.sql`
2. `0011_ppr_equipment_qr.sql`
3. `0012_ppr_templates_assignments.sql`
4. `0013_ppr_calendar.sql`
5. `0014_ppr_tasks.sql`
6. `0015_ppr_files.sql`
7. `0016_ppr_rls.sql`
8. `0017_ppr_cron_rpc.sql`

Конвенция:

- attachment tables создаются вместе с родительскими сущностями
- `0015_ppr_files.sql` используется только для storage/bucket/policies и не создает доменные attachment tables

## 5. Этап 0: подготовка архитектуры

### Цель

Подготовить каркас модуля, чтобы дальнейшая разработка шла в правильных границах.

### Что делаем

- создаем пустой namespace `ppr` в `app/(dashboard)`, `app/api`, `components`, `lib`, `app/actions`
- добавляем вход в модуль ППР в desktop navigation
- определяем mobile navigation-стратегию без перегрузки нижних табов
- фиксируем правила именования файлов и таблиц
- фиксируем статусы `ppr_tasks`
- фиксируем матрицу ролей с учетом `object_engineer`
- фиксируем окончательное правило доступа:
  - `admin` — полный доступ
  - `chief` — глобальный доступ ко всем объектам ППР без ограничения через `user_objects`
  - остальные роли — доступ в рамках `user_objects`, своих систем и своих заявок
- фиксируем UI-стратегию без локального `shadcn/ui`

### Результат этапа

- каркас модульной структуры
- единая договоренность по архитектуре
- отсутствие риска смешения с `tasks`

### Что не делаем на этапе

- не пишем полный UI
- не реализуем cron
- не делаем сложные формы

### Что должно появиться уже на этом этапе по RLS

- базовые SQL helper functions:
  - `ppr_current_role()`
  - `ppr_has_object_access(_object_id uuid)`
  - `ppr_can_manage_object_scope(_object_id uuid)`
  - `ppr_can_be_system_responsible(_user_id uuid)`
- базовая логика для `chief` как глобальной роли ППР
- базовый каркас `lib/ppr/permissions.ts`

## 6. Этап 1: справочники и структура

### Цель

Собрать базовую иерархию ППР и карточку оборудования.

### Таблицы

- `ppr_system_groups`
- `ppr_systems`
- `ppr_subsystems`
- `ppr_rooms`
- `ppr_equipment`
- `ppr_equipment_attachments`
- `ppr_equipment_qr_codes`

### Ограничения и индексы, которые вводим сразу

- `ppr_system_groups`
  - `unique (code)`
  - `unique (name)`
- `ppr_systems`
  - `unique (object_id, name)`
  - индексы по `object_id`, `responsible_user_id`, `system_group_id`
- `ppr_subsystems`
  - `unique (system_id, parent_id, name)`
  - индексы по `object_id`, `system_id`, `parent_id`
- `ppr_rooms`
  - `unique (object_id, name)`
  - индекс по `object_id`
- `ppr_equipment`
  - `unique (inventory_no)`
  - индексы по `object_id`, `system_id`, `subsystem_id`, `room_id`, `status`
- `ppr_equipment_attachments`
  - `unique (storage_path)`
  - индексы по `object_id`, `equipment_id`, `uploaded_by`
- `ppr_equipment_qr_codes`
  - `unique (qr_token)`
  - `unique (equipment_id)` для одного активного QR
  - индекс по `object_id`

### Что делаем

- создаем группу систем как глобальный справочник
- создаем системы внутри объекта
- добавляем `responsible_user_id` в систему
- создаем древовидные подсистемы
- создаем помещения по объектам
- создаем оборудование с обязательной привязкой:
  - `object_id`
  - `system_id`
  - `subsystem_id`
  - `room_id`
- реализуем автоматический `inventory_no`
- реализуем генерацию `qr_token`
- добавляем карточку оборудования
- оставляем секцию "История ремонтов" как placeholder без реализации отдельного модуля ремонтов

### UI-экраны

- `/ppr/systems`
- `/ppr/subsystems`
- `/ppr/rooms`
- `/ppr/equipment`
- `/ppr/equipment/[id]`

### Server actions

- создание и редактирование систем
- создание и редактирование подсистем
- создание и редактирование помещений
- создание и редактирование оборудования

### Проверки и ограничения

- `responsible_user_id` допускает только:
  - `lead`
  - `engineer`
  - `object_engineer`
- `tech` нельзя выбрать ответственным
- все сущности кроме `ppr_system_groups` имеют `object_id`
- для object-bound таблиц сразу вводится базовый RLS по `object_id`
- `chief` сразу получает глобальный доступ к структуре ППР без фильтрации через `user_objects`

### Критерий завершения

- можно создать объектовую структуру ППР
- можно создать оборудование
- у оборудования есть инвентарный номер и QR

- базовый RLS для шаблонов и назначений внедряется уже на этом этапе
- helper functions для structure/templates/assignments не откладываются до финала

### Критерий завершения

## 8. Этап 3: календарь

### Цель

Построить месячный план ППР и разнос работ по дням.

### Таблицы

- `ppr_month_plans`
- `ppr_month_plan_items`

### Ограничения и индексы, которые вводим сразу

- `ppr_month_plans`
  - `unique (object_id, system_id, plan_month)`
  - индексы по `object_id`, `system_id`, `plan_month`
- `ppr_month_plan_items`
  - `unique (month_plan_id, assignment_id, source_due_date)`
  - индексы по `object_id`, `month_plan_id`, `system_id`, `equipment_id`, `planned_for`, `task_id`

### Что делаем

- формируем месячный план по активным назначениям
- рассчитываем плановые вхождения по правилу "каждые N месяцев от даты старта"
- показываем просроченные позиции
- показываем перенесенные позиции
- позволяем ответственному по системе разнести работы по дням
- если день не указан, `planned_for` устанавливается на `1` число месяца

### UI-экраны

- `/ppr/calendar`
- при необходимости карточка системы или фильтр по системе

### Кто работает с календарем

- `admin`
- `chief`
- `lead`
- `object_engineer`
- `engineer`, если он ответственный по системе

### Кто не работает с календарем

- `tech`

### Важные проектные правила

- календарь не назначает исполнителя
- календарь только определяет день создания заявки
- перенос с прошлого месяца должен попадать в текущий план
- RLS и SQL helper functions календаря появляются уже в этом этапе
- `chief` работает с календарем глобально по всему модулю ППР
- связь `ppr_month_plan_items -> ppr_tasks` является `M:1`
- `task_id` в `ppr_month_plan_items` заполняется только на этапе materialization/create-tasks
- materialization идет по `(object_id, equipment_id, planned_for)`
- lifecycle `ppr_month_plan_items` должен быть зафиксирован уже на этом этапе:
  - `pending`
  - `materialized`
  - `carried_over`
  - `closed`
  - `cancelled`

### Критерий завершения

- ответственный видит план на месяц
- может разнести работы по дням
- просроченные и перенесенные позиции корректно отображаются

## 9. Этап 4: ППР-заявки

### Цель

Реализовать полный lifecycle ППР-заявки от создания до архива.

### Таблицы

- `ppr_tasks`
- `ppr_task_work_items`
- `ppr_task_comments`
- `ppr_task_attachments`

### Ограничения и индексы, которые вводим сразу

- `ppr_tasks`
  - partial unique index для правила:
    - одна активная `ppr_task` на одно оборудование и одну плановую дату
    - активные статусы: `new`, `in_progress`, `done`
  - индексы по `object_id`, `system_id`, `equipment_id`, `responsible_user_id`, `assignee_id`, `status`, `planned_for`, `closed_at`, `cancelled_at`
- `ppr_task_work_items`
  - `unique (task_id, assignment_id)`
  - `unique (task_id, sort_order)`
  - индексы по `object_id`, `task_id`, `assignment_id`, `plan_item_id`
- `ppr_task_comments`
  - индексы по `object_id`, `task_id`, `author_id`, `created_at`
- `ppr_task_attachments`
  - `unique (storage_path)`
  - индексы по `object_id`, `task_id`, `comment_id`, `uploaded_by`

### Что делаем

- создаем ППР-заявки автоматически из календаря
- агрегируем несколько работ в одну заявку по правилу:
  - `object_id`
  - `equipment_id`
  - `planned_for`
- храним блоки работ в `ppr_task_work_items`
- `responsible_user_id` в `ppr_tasks` фиксируем как snapshot на момент создания заявки
- фиксируем snapshot-поля в `ppr_task_work_items`:
  - `title_snapshot`
  - `description_snapshot`
  - `methodology_snapshot`
  - `norm_hours_snapshot`
  - `checklist_snapshot`
- `checklist_snapshot` храним в структурированном `jsonb`
- назначаем исполнителя
- переводим в `in_progress`
- переводим в `done`
- требуем комментарий и фото для `done`
- закрываем через ответственного
- реализуем перенос
- реализуем отмену
- делаем архив по статусам `closed` и `cancelled`

### UI-экраны

- `/ppr/my`
- `/ppr/tasks`
- `/ppr/tasks/[id]`
- `/ppr/archive`

### API routes

- смена статуса
- назначение исполнителя
- перенос
- отмена
- комментарии
- фото

### Workflow-правила

- исполнитель:
  - открывает заявку
  - берет в работу
  - завершает
- ответственный:
  - назначает исполнителя
  - проверяет результат
  - закрывает
- если ответственный и исполнитель совпадают, допускается самостоятельное закрытие

### Важные проектные правила

- `done` не равно `closed`
- возврат на ознакомление лучше реализовывать не отдельным статусом, а выборкой задач `status=done`, где исполнитель не равен ответственному
- перенос изменяет дату текущей заявки, а не создает новую
- `cancelled` должен сопровождаться `cancelled_at`
- рекомендуется сразу хранить `cancelled_by`
- правило агрегации закрепляется не только в коде, но и в БД через partial unique index
- snapshots обязательны, чтобы изменения шаблона не ломали уже созданные заявки
- все plan items, вошедшие в одну materialized задачу, получают одинаковый `task_id`
- изменение `responsible_user_id` у системы не переписывает уже созданные заявки
- изменения ответственности по системе влияют только на будущие заявки
- перенос открытых заявок на нового ответственного допускается только отдельным explicit flow

### Критерий завершения

- ППР-заявка полностью проходит lifecycle
- комментарий и фото обязательны для завершения
- архив работает

## 10. Этап 5: права, PWA и полировка

### Цель

Закрыть безопасность, mobile UX и автопроцессы.

### Что делаем

- финализируем RLS на все таблицы `ppr_*`
- финализируем SQL helper functions для доступа
- закрываем object-bound доступ по `user_objects` для всех ролей, кроме `chief`
- настраиваем object_engineer-права
- делаем mobile-first упрощение экрана исполнителя
- внедряем QR-route
- внедряем единый orchestration cron route
- доводим аудит
- проверяем UX на телефоне

### RLS-фокус

- `tech` видит только свои заявки
- `engineer` видит свои заявки и свои системы
- `object_engineer` видит ППР по объектам из `user_objects`
- `lead` работает по объектам из `user_objects`
- `chief` имеет глобальный доступ ко всем объектам ППР
- `admin` видит все

### Что уже должно быть готово к началу этапа 5

- базовые helper functions для object access
- базовые policies на структуру, шаблоны и календарь
- базовые permission helpers в `lib/ppr/permissions.ts`

Этап 5 не должен начинаться с нуля по безопасности.
На нем происходит финализация и проверка полного набора правил, а не первое внедрение RLS.

### QR

- токенизированный переход `/ppr/qr/[token]`
- редирект в активную заявку или карточку оборудования

### Cron

- один orchestration route `/api/ppr/cron/run`
- идемпотентные шаги:
  - carryover
  - materialization
  - sync plan item statuses
- поддержка backfill по диапазону дат
- аудит системных событий через `audit_log` с:
  - `actor_id = null`
  - `meta.source = "cron"`
  - `meta.job`
  - `meta.run_id`
  - `action` с префиксом `system_*`

### Критерий завершения

- весь модуль работает с ролью и объектовым доступом
- mobile-сценарий исполнителя удобен
- cron-процессы отрабатывают безопасно

## 13. Основные риски реализации

- неправильное смешение `tasks` и `ppr_tasks`
- слишком позднее внедрение RLS
- неправильная трактовка `object_engineer`
- отсутствие snapshot-полей у work items
- отсутствие partial unique index на активные `ppr_tasks`
- слишком ранняя реализация cron до стабилизации модели календаря
- перегруженный mobile UI

## 15. Итог

Правильная стратегия разработки ППР для `unaittasks`:

- строить новый модуль как отдельный вертикальный срез
- опираться на текущий auth / object access / audit / layout / PWA каркас
- вводить предметные сущности поэтапно
- не начинать с "карточки заявки", пока не готовы структура, назначения и календарь
- отдельно и явно поддержать роль `object_engineer`
- трактовать `chief` как глобальную управляющую роль модуля ППР
- внедрять RLS и SQL helper functions поэтапно, а не откладывать до конца
