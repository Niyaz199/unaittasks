# API проекта

Документ составлен по текущей реализации `app/api/**/route.ts` и связанным auth/permission helper'ам. Это не внешний OpenAPI-контракт, а практическое описание реально существующих route handlers в приложении.

## Общая картина

- Технология API: `Next.js App Router`, route handlers в `app/api`.
- Основная авторизация: `getApiSession()` -> request-scoped session из Supabase.
- Базовый формат успешного ответа: обычно JSON вида `{ ok: true, ... }`.
- Базовый формат ошибки: обычно JSON вида `{ error: "..." }` c HTTP-статусом `400/401/403/404/409/500`.
- Валидация входных данных: чаще всего через `zod`; загрузка файлов идет через `multipart/form-data`.
- Основные домены API:
  - обычные задачи;
  - ППР;
  - обходы помещений;
  - push-уведомления;
  - cron-эндпоинты.

## Общие правила доступа

### Пользовательские API

Почти все пользовательские маршруты используют `getApiSession()`:

- если нет сессии или профиля, обычно возвращается `401 Unauthorized`;
- затем выполняется проверка роли или предметных прав;
- при нехватке прав возвращается `403`.

### Cron API

Cron-маршруты не используют пользовательскую сессию. Они защищаются заголовком:

- `x-cron-secret: <CRON_SECRET>`

Если `CRON_SECRET` не задан или секрет неверен, cron-обработчики возвращают ошибку.

## Сводка по группам

### 1. Tasks API

Маршруты обычного task-flow.

| Метод | Путь | Назначение |
|------|------|------------|
| `POST` | `/api/tasks/[id]/team` | Добавить участника в команду задачи |
| `DELETE` | `/api/tasks/[id]/team` | Удалить участника из команды задачи |
| `POST` | `/api/tasks/[id]/comments` | Добавить комментарий к задаче |
| `POST` | `/api/tasks/[id]/pause` | Поставить задачу на паузу |
| `POST` | `/api/tasks/[id]/status` | Изменить статус задачи |
| `POST` | `/api/tasks/[id]/attachments` | Загрузить вложения к задаче или комментарию |
| `GET` | `/api/tasks/[id]/attachments` | Получить список вложений и signed URL |
| `POST` | `/api/tasks/[id]/archive` | Архивировать завершенную задачу |
| `GET` | `/api/tasks/[id]/history` | Получить историю задачи |

#### `POST /api/tasks/[id]/team`

- Назначение: добавить пользователя в команду задачи.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ userId: string }`
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401` -> нет сессии
  - `403` -> нет прав
  - `404` -> задача не найдена
  - `400` -> ошибка валидации или бизнес-логики

#### `DELETE /api/tasks/[id]/team`

- Назначение: убрать пользователя из команды задачи.
- Авторизация и структура параметров: те же, что у `POST /team`.

#### `POST /api/tasks/[id]/comments`

- Назначение: создать комментарий к задаче.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ body: string, clientMsgId?: string }`
- Особенности:
  - есть дедупликация по `clientMsgId`;
  - после добавления комментария могут отправляться push-уведомления наблюдателям.
- Типовые ответы:
  - `200` -> `{ ok: true, commentId }` или dedupe-ответ
  - `401`, `403`, `404`, `400`

#### `POST /api/tasks/[id]/pause`

- Назначение: поставить задачу на паузу через RPC `pause_task`.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ reason: string, resumeAt: string }`
- Бизнес-правила:
  - причина должна быть содержательной;
  - дата восстановления должна быть в будущем.
- Типовые ответы:
  - `200` -> `{ ok: true, result }`
  - `400`, `401`, `403`, `404`

#### `POST /api/tasks/[id]/status`

- Назначение: изменить статус задачи.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ status: "new" | "accepted" | "in_progress" | "paused" | "done" }`
- Бизнес-правила:
  - фактически `paused` через этот маршрут запрещен;
  - для паузы нужно использовать отдельный endpoint `/pause`;
  - переходы статусов проверяются через permission helpers.
- Побочные эффекты:
  - обновляются даты `accepted_at` и `completed_at`;
  - пишется audit-событие.
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `400` -> невалидный переход или ошибка валидации
  - `401`, `403`, `404`

#### `POST /api/tasks/[id]/attachments`

- Назначение: загрузить файлы к задаче или к конкретному комментарию.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `multipart/form-data`
  - поля: `files[]`, опционально `comment_id`
- Типовые ответы:
  - `200` -> `{ ok: true, uploaded, errors }`
  - `400`, `401`, `403`, `404`

#### `GET /api/tasks/[id]/attachments`

- Назначение: вернуть вложения и signed URL на чтение.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `query`: `comment_id?`
- Типовые ответы:
  - `200` -> `{ ok: true, attachments }`
  - `401`, `403`, `404`

#### `POST /api/tasks/[id]/archive`

- Назначение: вручную архивировать завершенную задачу.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
- Бизнес-правила:
  - задача должна быть пригодна для архивации;
  - действие доступно только ролям с соответствующим правом.
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401`, `403`, `404`, `409`

#### `GET /api/tasks/[id]/history`

- Назначение: получить историю изменений задачи.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
- Типовые ответы:
  - `200` -> `{ ok: true, history }`
  - `401`, `403`, `400`

### 2. PPR API

Самый крупный блок API: lifecycle ППР-заявок, QR, импорт помещений и cron-оркестрация.

| Метод | Путь | Назначение |
|------|------|------------|
| `POST` | `/api/ppr/tasks/[id]/assign` | Назначить или снять исполнителя ППР-заявки |
| `POST` | `/api/ppr/tasks/[id]/status` | Перевести ППР-заявку в `in_progress` или `done` |
| `POST` | `/api/ppr/tasks/[id]/reschedule` | Перенести дату ППР-заявки |
| `POST` | `/api/ppr/tasks/[id]/cancel` | Отменить ППР-заявку |
| `POST` | `/api/ppr/tasks/[id]/comments` | Добавить комментарий к ППР-заявке |
| `POST` | `/api/ppr/tasks/[id]/attachments` | Загрузить вложения |
| `GET` | `/api/ppr/tasks/[id]/attachments` | Получить вложения и signed URL |
| `GET` | `/api/ppr/qr/[token]` | Разрешить общий ППР QR-token |
| `GET` | `/api/ppr/rooms/qr/[token]` | Разрешить room QR-token |
| `POST` | `/api/ppr/rooms/[id]/qr/regenerate` | Пересоздать QR комнаты |
| `POST` | `/api/ppr/rooms/import/preview` | Предпросмотр импорта помещений |
| `POST` | `/api/ppr/rooms/import/commit` | Подтвердить импорт помещений |
| `POST` | `/api/ppr/cron/monthly` | Запустить месячный цикл ППР |
| `POST` | `/api/ppr/cron/run` | Запустить daily orchestration ППР |

#### `POST /api/ppr/tasks/[id]/assign`

- Назначение: назначить исполнителя или снять назначение.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ assigneeId: string | null }`
- Бизнес-правила:
  - право проверяется через `canAssignPprTaskExecutor`;
  - если указан исполнитель, он должен пройти проверку `assertPprTaskAssigneeCandidate`.
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401`, `403`, `404`, `409`, `400`

#### `POST /api/ppr/tasks/[id]/status`

- Назначение: начать выполнение ППР-заявки или завершить ее.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ status: "in_progress" | "done" }`
- Бизнес-правила:
  - права зависят от роли и текущего состояния заявки;
  - для `done` требуется минимум один комментарий и минимум одно фото;
  - используется optimistic concurrency check по текущему статусу.
- Побочные эффекты:
  - пишется audit;
  - обновляются связанные PPR-страницы через `revalidatePath`.
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `400` -> например, нет обязательного комментария или фото
  - `401`, `403`, `404`, `409`

#### `POST /api/ppr/tasks/[id]/reschedule`

- Назначение: изменить дату `plannedFor`.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ plannedFor: "YYYY-MM-DD", reason: string }`
- Бизнес-правила:
  - перенос разрешен только в рамках того же календарного месяца;
  - нельзя перенести на ту же дату;
  - обновляется логика статуса plan item'ов.
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401`, `403`, `404`, `409`, `400`

#### `POST /api/ppr/tasks/[id]/cancel`

- Назначение: отменить ППР-заявку с указанием причины.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ reason: string }`
- Бизнес-правила:
  - доступно только при разрешенном lifecycle-переходе;
  - синхронизируются связанные plan item'ы.
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401`, `403`, `404`, `409`

#### `POST /api/ppr/tasks/[id]/comments`

- Назначение: добавить комментарий к ППР-заявке.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `body`: `{ body: string }`
- Типовые ответы:
  - `200` -> `{ ok: true, commentId }`
  - `401`, `403`, `404`, `400`

#### `POST /api/ppr/tasks/[id]/attachments`

- Назначение: загрузить файлы к ППР-заявке или ее комментарию.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `multipart/form-data`
  - поля: `files`, опционально `comment_id`
- Бизнес-правила:
  - число файлов за одну загрузку ограничено;
  - каждый файл проходит отдельную валидацию;
  - если указан `comment_id`, комментарий должен принадлежать этой заявке.
- Типовые ответы:
  - `200` -> `{ ok: true, uploaded, errors }`
  - `401`, `403`, `404`, `400`

#### `GET /api/ppr/tasks/[id]/attachments`

- Назначение: получить вложения ППР-заявки.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `path`: `id`
  - `query`: `comment_id?`
- Типовые ответы:
  - `200` -> `{ ok: true, attachments }`
  - `401`, `403`, `404`

#### `GET /api/ppr/qr/[token]`

- Назначение: разрешить QR-токен ППР и перенаправить пользователя в нужную сущность.
- Авторизация: нужна сессия; при ее отсутствии редирект на `/login`.
- Вход:
  - `path`: `token`
- Поведение:
  - возвращает redirect к карточке оборудования, активной ППР-заявке или на промежуточную страницу ППР QR flow.

#### `GET /api/ppr/rooms/qr/[token]`

- Назначение: разрешить QR-токен комнаты.
- Авторизация: нужна сессия и право на чтение комнат; иначе редирект на `/login`.
- Вход:
  - `path`: `token`
- Поведение:
  - возвращает redirect к карточке комнаты или на промежуточный room QR flow.

#### `POST /api/ppr/rooms/[id]/qr/regenerate`

- Назначение: пересоздать QR-код комнаты.
- Авторизация: нужна сессия и право управления комнатами.
- Вход:
  - `path`: `id`
- Типовые ответы:
  - `200` -> `{ ok: true, qrCode }`
  - `401`, `403`, `400`

#### `POST /api/ppr/rooms/import/preview`

- Назначение: загрузить CSV/XLSX и получить превью импорта помещений.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `multipart/form-data`
  - поле: `file`
- Выход:
  - превью распарсенных строк и результатов валидации.
- Типовые ответы:
  - `200` -> preview payload
  - `401`, `400`

#### `POST /api/ppr/rooms/import/commit`

- Назначение: зафиксировать импорт помещений.
- Авторизация: нужна сессия и профиль.
- Вход:
  - `body`: `{ rows: [...] }`
- Бизнес-правила:
  - максимум до `500` строк за операцию;
  - импорт работает в режиме `create only`;
  - дубликаты пропускаются, ошибки собираются по строкам.
- Побочные эффекты:
  - выполняется revalidate для экранов справочников, ППР и обходов.
- Типовые ответы:
  - `200` -> `{ ok: true, summary, errors }`
  - `401`, `400`

#### `POST /api/ppr/cron/monthly`

- Назначение: monthly cycle ППР.
- Авторизация: только через `x-cron-secret`.
- Вход:
  - `body` опционален: `{ anchor_date?: "YYYY-MM-DD", run_id?: string }`
- Выход:
  - `{ ok: true, run_id, ... }`
- Типовые ответы:
  - `200`, `400`, `401`, `500`

#### `POST /api/ppr/cron/run`

- Назначение: daily orchestration ППР по диапазону дат.
- Авторизация: только через `x-cron-secret`.
- Вход:
  - `body`: `{ date_from: "YYYY-MM-DD", date_to: "YYYY-MM-DD", run_id?: string }`
- Бизнес-правила:
  - `date_from <= date_to`.
- Выход:
  - `{ ok: true, run_id, ... }`
- Типовые ответы:
  - `200`, `400`, `401`, `500`

### 3. Rounds API

API модуля обходов помещений.

| Метод | Путь | Назначение |
|------|------|------------|
| `GET` | `/api/rounds/archive` | Архив обходов |
| `GET` | `/api/rounds/today` | Журнал обходов за сегодня |
| `GET` | `/api/rounds/resolve/[token]` | Resolve QR-токена помещения для scanner flow |
| `POST` | `/api/rounds/checkins` | Сохранить отметку обхода |
| `GET` | `/api/rounds/config` | Получить конфигурацию scanner/config screens |
| `POST` | `/api/rounds/config` | Сохранить конфигурацию обходов |
| `POST` | `/api/rounds/qr/generate` | Legacy endpoint, возвращает `410 Gone` |
| `GET` | `/api/rounds/qr/[token]` | Deep link по QR-токену помещения |

#### `GET /api/rounds/archive`

- Назначение: отдать архив обходов для отчетных экранов.
- Авторизация: нужна сессия, профиль и право `canReadRoundsReports`.
- Вход:
  - `query`: `objectId`, `roomId`, `technicianId`, `technician`, `q`, `dateFrom`, `dateTo`
- Типовые ответы:
  - `200` -> `{ ok: true, ...result }`
  - `401`, `403`, `400`

#### `GET /api/rounds/today`

- Назначение: отдать данные журнала обходов за текущий операционный день.
- Авторизация: нужна сессия, профиль и право `canReadRoundsReports`.
- Вход:
  - `query`: `objectId`, `operationalDate`, `q`
- Типовые ответы:
  - `200` -> `{ ok: true, ...result }`
  - `401`, `403`, `400`

#### `GET /api/rounds/resolve/[token]`

- Назначение: resolve shared room QR-token для scanner flow.
- Авторизация: нужна сессия, профиль и право `canUseRoundsScanner`.
- Вход:
  - `path`: `token`
- Выход:
  - JSON со state результата, например `configured`, `inactive`, `disabled`, `invalid`.
- Типовые ответы:
  - `200`
  - `401`, `403`, `400`

#### `POST /api/rounds/checkins`

- Назначение: сохранить check-in обхода, включая фото.
- Авторизация: нужна сессия, профиль и право `canUseRoundsScanner`.
- Вход:
  - `multipart/form-data`
  - поля: `room_id`, `client_event_id`, `scanned_at_device`, `comment`, `source`, опционально `photo`
- Бизнес-правила:
  - повторная отметка за день сравнивается по времени устройства;
  - маршрут поддерживает online submit из scanner flow и offline sync.
- Типовые ответы:
  - `200` -> `{ ok: true, checkin }`
  - `400` -> может содержать `details` или `hint`
  - `401`, `403`

#### `GET /api/rounds/config`

- Назначение: получить конфиг scanner/config экранов.
- Авторизация: нужна сессия и профиль.
- Выход:
  - данные по доступным объектам, помещениям и timezone.
- Типовые ответы:
  - `200`
  - `401`, `400`

#### `POST /api/rounds/config`

- Назначение: сохранить выбор помещений для обходов.
- Авторизация: нужна сессия, профиль и право `canManageRoundsConfig`.
- Вход:
  - либо single-object payload;
  - либо batch payload `{ operations: [...] }`.
- Особенности:
  - поддерживает partial success;
  - при частичном выполнении может возвращать `207 Multi-Status`.
- Типовые ответы:
  - `200`, `207`, `400`, `401`, `403`

#### `POST /api/rounds/qr/generate`

- Назначение: legacy endpoint.
- Поведение:
  - QR для обходов больше не генерируются этим вызовом;
  - маршрут возвращает `410 Gone`.

#### `GET /api/rounds/qr/[token]`

- Назначение: deep link по room QR.
- Авторизация:
  - если нет сессии, редирект на `/login`;
  - при наличии прав перенаправляет на scanner flow.
- Вход:
  - `path`: `token`
- Поведение:
  - redirect на `/rounds/scan?token=...` или на логин.

### 4. Push API

Маршруты web-push подписок и отправки уведомлений.

| Метод | Путь | Назначение |
|------|------|------------|
| `POST` | `/api/push/subscribe` | Сохранить push-подписку текущего пользователя |
| `POST` | `/api/push/test` | Отправить тестовый push текущему пользователю |
| `GET` | `/api/push/test` | Возвращает `405`, тестовый маршрут не поддерживает GET |
| `POST` | `/api/push/send-assignment` | Отправить push о назначении задачи |

#### `POST /api/push/subscribe`

- Назначение: upsert подписки в таблицу `push_subscriptions`.
- Авторизация: нужна пользовательская сессия.
- Вход:
  - `body`:
    - `endpoint`
    - `keys.p256dh`
    - `keys.auth`
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401`, `400`

#### `POST /api/push/test`

- Назначение: отладочно отправить тестовое push-уведомление текущему пользователю.
- Авторизация: нужна пользовательская сессия.
- Типовые ответы:
  - `200` -> успешная отправка
  - `401`
  - `500` -> ошибка отправки
  - `503` -> VAPID не настроен

#### `GET /api/push/test`

- Назначение: явно показать, что `GET` не поддерживается.
- Типовые ответы:
  - `405`

#### `POST /api/push/send-assignment`

- Назначение: отправить push о новой задаче назначенному исполнителю.
- Авторизация: нужна сессия и право `canEditTasks`.
- Вход:
  - `body`: `{ taskId, assignedTo, taskTitle, objectName? }`
- Типовые ответы:
  - `200` -> `{ ok: true }`
  - `401`, `403`, `400`

### 5. Cron API

Общие системные cron-маршруты вне ППР.

| Метод | Путь | Назначение |
|------|------|------------|
| `POST` | `/api/cron/archive` | Архивировать завершенные обычные задачи |

#### `POST /api/cron/archive`

- Назначение: вызвать RPC `archive_done_tasks`.
- Авторизация: через `x-cron-secret`, если `CRON_SECRET` задан.
- Особенности:
  - использует admin client;
  - порог архивирования привязан к серверной логике.
- Типовые ответы:
  - `200` -> `{ ok: true, archived }`
  - `401`, `400`

## Кто и как потребляет API

### Основные потребители

- `components/tasks/*` -> lifecycle обычных задач, команда, комментарии, вложения.
- `components/ppr/tasks/*` и `components/ppr/rooms/*` -> lifecycle ППР, вложения, QR, импорт.
- `components/rounds/*` -> scanner flow, config, QR resolve, check-in.
- `components/pwa/*` -> push subscription.
- offline-очередь:
  - `lib/offline/queue.ts` использует task comment/status endpoints;
  - `lib/offline/rounds-queue.ts` использует rounds check-in endpoint.

### Важная особенность архитектуры

Часть экранов в приложении использует не fetch к `/api`, а прямой вызов серверных функций из `lib/*`. Поэтому API здесь часто дублирует серверный контракт, а не всегда является единственным способом получить данные.

Это особенно заметно в:

- `rounds today/archive`;
- `tasks history`;
- части PPR read-model логики.

## Основные паттерны проекта

### 1. API тесно связан с ролями

Практически каждый mutating endpoint завязан не только на факт логина, но и на доменные permission helpers:

- `task-permissions`
- `rounds/permissions`
- `ppr/task-lifecycle`
- `object room`-права

### 2. Файлы и фото идут через storage

Обычные задачи, ППР и обходы используют upload flow через storage, а на чтение обычно отдаются signed URL.

### 3. Есть offline-friendly сценарии

Не весь API offline-ready, но есть важные исключения:

- статус и комментарии обычных задач;
- check-in обходов, включая фото.

### 4. PPR API самый сложный

Именно блок `PPR` содержит больше всего бизнес-правил:

- lifecycle заявки;
- условия завершения;
- перенос только внутри месяца;
- cron orchestration;
- импорт помещений;
- QR resolve flows.

## Итог

В проекте сейчас реализован внутренний прикладной API из пяти больших групп:

1. `Tasks API` для обычных эксплуатационных задач.
2. `PPR API` для планово-предупредительных работ, импорта и QR.
3. `Rounds API` для обходов помещений и scanner flow.
4. `Push API` для web-push сценариев.
5. `Cron API` для фоновых автоматических операций.
